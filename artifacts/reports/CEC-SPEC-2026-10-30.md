## 1. The bus

* One wire, wired-AND, ~**2.4 ms per data bit** (nominal) — a bit under 420 bit/s. A start bit is
  ~3.7 ms low.
* Every block is **10 bits**: 8 information bits + **EOM** + **ACK**. EOM=1 marks the last block.
* **Header block** = `initiator << 4 | destination`. Destination `15` = broadcast, initiator `15` =
  unregistered.
* **Max 16 blocks** total (header + 15 data), so a message is at most 16 bytes on the wire.
* A frame that isn't acknowledged may be re-sent **up to 5 times**, at least once.
* Directed acknowledgment pulls the line low for ACK, not NACK; broadcast
  acknowledgment uses different rules. A 1.4–1.6× bit-period low
  pulse is an error notification and aborts the message.

## 2. Addressing

Physical address = **the HDMI tree position**, `A.B.C.D`. The TV (root) is `0.0.0.0`; the device on
HDMI1 gets `1.0.0.0`, HDMI2 `2.0.0.0`, and so on. Logical address = *what the device is*:

```
0 TV (only at physical 0.0.0.0)     5 Audio System      10 Tuner 4
1 Recording Device 1                6 Tuner 2           11 Playback Device 3
2 Recording Device 2                7 Tuner 3           12,13 Reserved
3 Tuner 1                           8 Playback Device 2 14 Free Use
4 Playback Device 1                 9 Recording Device 3 15 Unregistered / broadcast
```

Rules that matter in practice:

* a device may only claim a logical address once it has a valid physical address;
* allocation is done by polling each candidate address with a `<Polling Message>` (a header block with
  no data) and taking the first one nobody answers;
* on discovering a new physical address a device **shall** allocate a logical address and
  **broadcast `<Report Physical Address>`** — this is how everyone builds the map;
* one physical device may hold several logical addresses (e.g. `4` and `5`), which is exactly the
  peer-link we found in `NovoCECController::setDevicePhysicalAddress` (`+0x150`, two LAs on one PA).

## 3. The features this TV actually uses

### One Touch Play — `0x04 <Image View On>` / `0x0D <Text View On>` + `0x82 <Active Source>`

A source that wants to be shown sends `<Image View On>` to the TV (TV powers up / switches to Image
state) and then broadcasts `<Active Source>` with its own physical address. `<Text View On>` is the
same but also clears any menu on screen. The source shall send `<Active Source>` only once it has
stable video.

### Routing Control — `0x80 <Routing Change>`, `0x81 <Routing Information>`, `0x82 <Active Source>`, `0x86 <Set Stream Path>`

How the TV selects an input. The TV sends `<Set Stream Path>` with the target physical address; the
device at that address comes out of standby, and when it has video it broadcasts `<Active Source>`.
A CEC switch that changes route broadcasts `<Routing Change>` (old PA, new PA); the switch at the new
position answers with `<Routing Information>`.

### `0x85 <Request Active Source>` — the one aurora works around

When the TV comes out of standby it may not know who is the active source (it was off when the
device announced). The spec says it may broadcast `<Request Active Source>`; the current active
source **must** answer with `<Active Source>`. If nothing answers, the TV has to infer the input.

This is precisely the gap aurora patches with its LA-4 state machine
(`_ice_cec_Handler`, see `SOURCES-CEC-2026-10-30.md`): it waits for *either* `Set OSD Name` *or*
`Report Power Status = On` from logical address 4 and then broadcasts `<Request Active Source>` —
i.e. it forces the handshake for devices that only announce themselves by name/power rather than by
`<Active Source>`. It is a workaround, not a spec deviation: the spec allows the TV to ask at any
time.

### Device OSD Name Transfer — `0x46 <Give OSD Name>`, `0x47 <Set OSD Name>`

Verbatim, CEC 13.11.2:

> This feature is used to request the preferred name of a device to be used in any on screen display
> (e.g. menus), which reference that device. A device (e.g. the TV) may request another devices name
> by sending a directly addressed `<Give OSD Name>` message to it. If the device supports this
> feature it shall respond with a `<Set OSD Name>` message. The devices name should then be
> **stored and used in any future on screen references to it**.
>
> A TV may send a `<Give OSD Name>` message **whenever it discovers a new device** that has been
> connected.

Operand `[OSD Name]` = `N {[ASCII]}, 1 ≤ N ≤ 14` — **1 to 14 bytes**.
From CEC Table 17 both messages are **directly addressed only** (the broadcast column is empty), and
the follower's required response to `<Set OSD Name>` is literally *"Store the name and use it in any
menus associated with that device"*.

This vindicates everything we reverse-engineered from `aurora.elf` — the 14-byte truncation, the
directed-only check in `isMessageValid`, the per-logical-address store, and `getExternalInterfaceName`
preferring the stored name. Vestel implemented 13.11 faithfully. The one thing the spec does **not**
require is persistence, and aurora keeps it in RAM (re-learned each boot) — conformant, if slightly
unhelpful.

### `0x8F <Give Device Power Status>` / `0x90 <Report Power Status>`

Ask a device whether it is On / Standby / In transition; it answers. Used before sending `<Play>` or
`<Image View On>`, and the reason the LA-4 workaround keys on `Report Power Status = On`.

### `0x36 <Standby>`

Broadcast (or directed) to put devices into standby. The TV also advertises its own power state.

### System Audio Control / ARC — `0x70`, `0x71`, `0x72`, `0x7A`, `0x7D`, `0x7E`, `0xC0`–`0xC5`

Volume/mute routing uses the base System Audio feature; ARC requires CEC 1.4.
**Corrected:** the Audio System (ARC receiver) sends Initiate ARC (`0xC0`) to
the TV (ARC transmitter), which reports initiation (`0xC1`) or termination (`0xC2`).
The TV can request initiation (`0xC3`) or termination (`0xC4`); the Audio System
sends Terminate ARC (`0xC5`). Adjacency, capabilities and hardware state are
required too. See CEC-AUDIO-CONTRACT for clauses and acceptance limits.

### Remote Control Pass Through — `0x44 <User Control Pressed>` / `0x45 <User Control Released>`

Key presses forwarded to another device. Codes `0x00`–`0x65` are just remote buttons; **`0x60`–`0x6D`
are deterministic Functions** (Play/Pause/Stop/Mute/… with exactly specified state after execution).
That is the table our `CECKeyMapper` maps into (`m_key_mapping`, ICE key → CEC user-control code), and
it is why the mapping is only meaningful for the subset of keys a device understands.

### Vendor — `0x89 <Vendor Command>`, `0xA0 <Vendor Command With ID>`, `0x8A/0x8B <Vendor Remote Button>`

Vendor-specific payloads. This is where Novatek/Vestel put their private traffic (the
`0xC3`/`0xA4`/`0x70` destination-rewriting `==WA==` hack we saw lives next to these).

## 4. Spec vs aurora — conformance table

| behaviour | spec | aurora | verdict |
|---|---|---|---|
| discover a device → ask its name | "may send `<Give OSD Name>` whenever it discovers a new device" | sends it on `<Report Physical Address>` and again on input switch if no name cached | conformant, more eager than required |
| respond to `<Set OSD Name>` | store and use in menus | `setHDMIName()`, per LA, preferred over user and factory names | conformant |
| name length | 1–14 ASCII | truncates to 14, rejects >14 | conformant |
| broadcast `<Set OSD Name>` | not allowed (directly addressed only) | rejected by `isMessageValid` | conformant |
| replies to `<Give OSD Name>` | shall (if feature supported) | — (this is the source side; the TV asks) | n/a |
| know the active source after standby | may broadcast `<Request Active Source>`, source **must** answer | LA-4 workaround fires `<Request Active Source>` on `Set OSD Name`/`Report Power Status` | conformant workaround |
| ARC setup | requires CEC 1.4 | static paths present | unverified; use CEC-AUDIO-CONTRACT |
| key passthrough | `0x44`/`0x45`, Functions `0x60`–`0x6D` | `CECKeyMapper` table | conformant |

This static inventory does not establish conformance or absence of deviations.
In particular 1.3a cannot validate ARC, and vendor workarounds still require
instruction/specification review and later wire-level acceptance.

## 5. So: the Steam Deck

Per 13.11.2 the Deck **shall** answer `<Give OSD Name>` with `<Set OSD Name>` *if it implements
Device OSD Name Transfer*. The old claim that unsupported directed requests may
simply be ignored was incorrect: CEC 12.3 requires the appropriate Feature Abort.
The TV can retain its fallback label when no usable name is received.

So there are exactly three outcomes, and they're distinguishable live:

1. **Deck answers 0x47** → the input is renamed to its advertised string (≤14 chars). This is what
   `setHDMIName` does, and it beats a manually set label.
2. **Deck ignores 0x46** → no rename; nothing can be done from the TV side except a manual label 
   (the TV can't invent a name).
3. **Deck answers but the name is useless** (e.g. `"Steam Deck"` truncated, or an empty/garbage
   payload) → we'd see a weird label.

Fallback that does **not** exist here: reading the source's EDID `0xFC` Display Product Name. On this
chassis the HDMI inputs are handled by `ntkndphdmi.ko` and never appear as DRM connectors —
`/sys/class/drm` only lists `card0-LVDS-1` / `card1-LVDS-2` — so there is no standard place to read
a source EDID from userspace. aurora gets it through ICE. So if the Deck doesn't do CEC naming, the
TV cannot learn its name at all.

How to confirm when the set is free (read-only once armed): watch `ice_cec` traffic / the input label
while the Deck is connected. Practically: connect the Deck, switch to its input, and see whether the
label changes from "HDMI x" after a few seconds.

## 6. If we ever implement CEC ourselves (native shell / device emulation)

Minimal TV-side state machine, in the order the spec implies:

```
boot:
  assign physical address 0.0.0.0 (root)            # the TV is always the root
  logical address = 0                                # only legal at 0.0.0.0
  <Report Physical Address> broadcast?               # a TV reports 0.0.0.0 + device type TV
  if we don't know the active source: <Request Active Source>
hotplug on an HDMI port:
  new PA exists → <Report Physical Address>-style bookkeeping, then <Give OSD Name> to that LA
  also <Give Device Power Status> if we may want to wake it
receive <Set OSD Name>:  store per LA (≤14), re-render any menu/label
receive <Report Physical Address>: record LA↔PA↔device-type, map PA → input
receive <Active Source>: switch to that PA's input, mark CEC
receive <Routing Change>/<Routing Information>: update the input map
receive <Report Power Status>: update the device's power state
send key: <User Control Pressed> + <User Control Released> with the [UI Command] code
standby: <Standby>; on wake: <Request Active Source>
ARC: TV requests initiation (C3); Audio System initiates (C0); TV reports (C1/C2)
```

The old MCU-UART transport attribution here was incorrect. This target sends
normal frames through private V4L2 controls into the kernel CEC driver in
ntkdriver_nondovi. MCU enable/wake/authority policy is separate. Read
[CEC-TRANSPORT-CONTRACT](CEC-TRANSPORT-CONTRACT-2026-10-31.md) before implementing;
packet layouts, driver filtering and close/reopen all have significant pitfalls.
