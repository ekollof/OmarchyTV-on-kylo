# The UI stack: how aurora draws, and where we can plug in (2026-10-30)

> **Status: Historical stack survey/options. Native replacement is active; presumed spare-plane and web recommendation are not current plans.** See [report index](README.md) and
> [current corrections](../../FINDINGS.md); old plans do not authorize TV changes.

## 1. There is no X / Wayland / Qt — it is DirectFB straight onto OSD layers

`aurora.elf` (135 DT_NEEDED entries) links the classic DirectFB 1.7 stack:

```
libdirectfb-1.7.so.1   libfusion-1.7.so.1   libfusiondale-1.7.so.1   libsawman-1.7.so.1
libomi.so   libmpc_api.so   libmali.so   libdrm.so.2   libgstreamer-1.0 + libgstnvtsink.so
```

Installed under `/vendor/lib/dfb/directfb-1.7-1`:

| part | module |
|---|---|
| system | `libdirectfb_fbdev.so` → `open()`+`mmap()` on `/dev/fbX` |
| gfxdriver | `libdirectfb_tdga.so` (Novatek TDGA 2D blitter) |
| wm | `libdirectfbwm_sawman.so` (SawMan), `libdirectfbwm_default.so` |
| input | `libdirectfb_nvt_uart_ir.so` (IR receiver on UART) |
| interfaces | `IDirectFBFont`, `IDirectFBImageProvider`, `IDirectFBVideoProvider` |

Config `/vendor/etc/mp/.directfbrc`:

```
system=fbdev
mode=1920x1080   pixelformat=ARGB   depth=32
wm=sawman        no-cursor          no-layers-clear
init-layer=0     layer-stacking=middle,upper
init-layer=1     layer-stacking=lower
no-neon
```

So the app owns the display: `aurora` holds **all five** OSD framebuffers open
(`fb0..fb4`), plus `/dev/mali0` (Mali GL) and `/dev/dri/card0`.
`/proc/fb` lists them as `OSD_NORMAL1/2/3`, `OSD_CURSOR1/2` — i.e. the
DirectFB "layers" are the SoC's hardware OSD planes, each its own
triple/double-buffered mapping:

| node | name | geometry | bpp | observed use |
|---|---|---|---|---|
| `/dev/fb0` | OSD_NORMAL1 | 1920×3240 (3×1080) | 32 | app/video OSD; all-zero (transparent) when idle |
| `/dev/fb1` | OSD_NORMAL2 | 1920×2160 (2×1080) | 32 | **launcher, menus, dialogs, no-signal banner** |
| `/dev/fb2` | OSD_NORMAL3 | 1280×1440 (2×720) | 16 | extra 720p plane, currently unused |
| `/dev/fb3` | OSD_CURSOR1 | 256×512 | 32 | hardware cursor layer (`no-cursor`) |
| `/dev/fb4` | OSD_CURSOR2 | 32×64 | 32 | hardware cursor layer |

Video is *not* drawn through the fb: GStreamer + `gstnvtsink` push frames to the
video plane; the fb layers are the graphics OSD above it.

## 2. The look of the UI is data, not code

```
/vendor/dynamic_ui -> /vendor2/dynamic_ui
    default.ui                     theme name + version ("telefunken18", V.0.51.52.3)
    telefunken18_svg.bin   .txt    layout records (name, properties; not literal SVG artwork)
    telefunken18_img.bin   .txt    bitmaps        (name, hash, w, h, offset)
    telefunken18_font_byte_data.bin/.txt   30 MB of baked glyph data
```

`aurora` renders the launcher/menus/settings from these packs (layout + PNG + font
atlas) — the `.txt` next to each `.bin` is the asset index. These packs carry substantial UI content; dynamic labels, downloaded tiles
and behavior also depend on profiles/settings/code. Full layout decoding remains open.

## 3. HTML apps run in a separate engine

`libomi.so` + `/vendor/browser_dir` (Opera/OMI engine, `omi_worker` processes) run
web content (`/vendor2/html_applications/digital_ib`: `index.htm`, `js/Keys.js`,
`js/Navigation.js`). `omi_worker` has **no** fd on `/dev/fb*`, so web pages render
off-screen and `aurora` composites their surface — that is why `browserseturl`
works (verified: the TV fetched `http://…/tvtest` 200) and why the page shows up
in the OSD layer.

## 4. Proof that we can paint the screen ourselves

Root can write the OSD layers; they are plain char devices, no signature involved:

* read `/dev/fb1` (16,588,800 B), stamped a magenta box into **both** frames,
  wrote it back with `dd of=/dev/fb1`, and the capture showed the box
  (`tools/tvshot.py`).
* restored the saved bytes → read-back md5 identical to the pre-test image
  (`41735daa…`), so the experiment left nothing behind.

Caveats: DirectFB keeps its own shadow state; it will repaint its regions on the
next update, may tear, and it does **not** know about our pixels. Write both
frames of a double-buffered layer (or use `FBIOPAN_DISPLAY`) so the visible buffer
is the one you painted.

## 5. Ways to add a custom UI

| route | what it means | effort | risk |
|---|---|---|---|
| **A. Re-skin** | replace `/vendor2/dynamic_ui` packs (needs a writable `--bind` overlay over the read-only squashfs) | low–med (must reverse the pack index) | none if content-identical sizes plan works |
| **B. Paint an overlay** | own process mmaps `fb1`/`fb2`, draws status/wallpaper/notifications | low | overwritten by aurora repaints; no input routing |
| **C. Own home screen in the boot chain** | the hook already runs *before* `exec /vendor/com.nvt.idtv/aurora.elf`; start our own full-screen painter there and exec aurora only when asked | med | two renderers on one layer unless we use a free plane (fb2) |
| **D. Web UI in the built-in browser** | serve a local page, load it with DIAL `browserseturl` (proved) | low | tied to the browser's lifetime; aurora can take the screen back |
| **E. Patch aurora** | `--bind` overlay of `/vendor` with a patched binary, or `LD_PRELOAD` shim into the DFB/ICE calls | high | glibc 2.23 hard-float ABI; must be redone per firmware |

Historical options only: the web route was later prototyped and its boot is
currently disabled. The active direction is independent native openaurora, not
concurrent painting on an assumed spare plane. See current TODO/OSD reports.

### Input, if we own the screen

Keys do not arrive on `/dev/input` (`/dev/input` only contains `mice`): the IR
receiver goes through `libdirectfb_nvt_uart_ir.so` into DirectFB/ICE
(`ICE_RemoteRegisterKeypressFunction`, the `vk_keymapping_db.xml` codes). A
custom UI therefore either (a) runs inside OMI where aurora feeds it keys, or
(b) is driven over the network (DIAL key POSTs) / by reading the IR UART itself,
which conflicts with the DFB input driver.

## 6. Open questions

- Is `/dev/fb2` (OSD_NORMAL3, 1280×720, 16bpp) scanned out / can it be enabled
  independently? If yes it is a free canvas for an overlay UI.
- Reverse the `dynamic_ui` `.bin`/`.txt` pack format (name → hash → offset).
- Whether `LD_PRELOAD` works on the vendor glibc 2.23 (would allow DFB-level
  interception without patching `aurora`).
