# OTA fetch mechanism — Callisto (aurora.elf, 0.51.52.3)

> **Status: Static Callisto research with specific-path observations. Not authorization to trigger updates, change network policy or flash firmware.** See [report index](README.md) and
> [current corrections](../../FINDINGS.md); old plans do not authorize TV changes.

Reverse-engineered from `aurora.elf` with Ghidra (project in `/tmp/opencode/ghidra_proj`,
outputs in `artifacts/reports/ghidra/`). Function addresses are from the ELF vaddr space.

## 1. Where the coordinates come from

The SW profile (`/conf/mb230_swprofile.bin`) carries:

```
7706.dcf            <- descriptor name   (Profile_GetDcfName)
0009df              <- project / OUI     (Profile_GetOui)
s3-eu-west-1.amazonaws.com/vstlupdate    <- host
SERVER_HTTP_SECURE_TYPE                  <- https
```

`ICE_CallistoGetDCFName` (0x7e6694):

```c
Profile_GetOui(oui);
Profile_GetDcfName(dcf);
snprintf(buf, 0x32, "/%s/%s", oui, dcf);      // -> "/0009df/7706.dcf"
```

So the descriptor URL is:

```
https://s3-eu-west-1.amazonaws.com/vstlupdate/0009df/7706.dcf
```

An anonymous GET of that object returns **403 AccessDenied** (S3 masks 403 for missing
keys when listing is denied, so the object may simply not exist for this build).

## 2. Descriptor applicability

`ICE_SoftwareUpdateIsDescriptionApplicable` (0x7890d4) takes `(type, id, model, version, current_version)`
and compares:

- `Profile_GetModelId()` and `ICE_SoftwareUpdateGetOUI()` against the descriptor's OUI/model,
- `versionRange(min-max)`, `customers:<list>`,
- `description_type`, `is_enhanced_oad`, `is_advertisement_oad`,
- current firmware version vs descriptor version.

Only a matching descriptor is offered to the user.

## 3. Signature and install

- `ICE_CallistoGetKey(index, out)` (0x7e68f8) returns **256-byte RSA keys**, index 1..9,
  from a table embedded in `.rodata` at **0x12dd3e6** (`9 × 0x100` bytes).
- `ICE_CallistoGetExpectedNumberOfSignatures` / `CHIL_*` equivalents define how many
  signatures the image must carry.
- `ICE_CallistoWriteBytesToFlash`, `ICE_CallistoActivateNewCode`, `CallistoIsActivateNewCode`
  write and switch the new image.
- Denied/rolled-back versions are tracked with
  `ICE_CallistoWriteDeniedWebSoftwareUpdateVersionToFile` / `...GetDenied...`.
- USB path: `ICE_CallistoCheckUsbToUpgrade`, `ICE_CallistoStartUpgradeSoftwareFromUSB`
  (the `kylo_usb_update` / `upgrade_mb230.bin` flows).
- `ICE_CallistoSetCustomSWUpgrade` allows a custom upgrade descriptor (service use).

The public keys are in the firmware, the private key is not — verification is one-way.

## 4. Not OTA: the 2 KB probes

`InternetMonitor` (0xa36560) fetches, over **plain HTTP**:

```
http://s3-eu-west-1.amazonaws.com/vstlupdate/Essentials/2kb.txt
http://s3-eu-west-1.amazonaws.com/vstlupdate/Essentials/speedtest.txt
http://www.portaltv.tv/assets/2kb.txt
```

These are connectivity/speed checks, not update traffic. (This is the `2kb.txt` seen in
the boot logs.)

## 5. What this means

- **Custom firmware via OTA is not possible**: RSA-2048 signatures + encrypted image,
  keys verified before write. This matches the Vestel security target.
- **With root we can still learn from it**: the descriptor fetch is a normal HTTPS GET.
  Capturing it (or reading the downloaded `.dcf` cache) yields the *signed XML descriptor*
  for this exact set — image name/version/path — which is exactly what we need to request
  the matching Telefunken package, and to confirm whether an OTA exists for 0.51.52.3.
- **OTA can be disabled** by blackholing `s3-eu-west-1.amazonaws.com` in `/conf/hosts`
  (not currently blocked — deliberately, so updates still work).
- The check is gated by the `m_auto_upgrade_on` setting and the denied-version file.

## 6. Signature key material (dumped)

`ICE_CallistoGetKey` exposes 9 keys of 256 bytes each from `.rodata` **0x12dd3e6**
(descriptor: `{type=0, count=1, size=0x100, ptr=base+(idx-1)*0x100}`), i.e. 2048-bit
material, most likely RSA moduli handed to the secure world for verification.

SHA-256 prefixes of the nine blobs (full blob in `/tmp/opencode/ota_keys.bin`):

```
k1 c2c5363646ede67d   k4 c7ab2ab913d4633a   k7 f019b0e77ff3dcea
k2 40acc63f97858a01   k5 278b705eeffcbefb   k8 4fb60edd3bcc381b
k3 fb66ed1e5b25f786   k6 31c859ef92130337   k9 2ca7e71b8b7a7e47
```

The exact type (RSA modulus vs. vendor key blob) is not confirmed — the consumer is
`CHIL_/ICE_CallistoGetExpectedNumberOfSignatures` plus the TEE, so the material may be
opaque to Linux. Worth a follow-up decompile of the verify call site.

## 7. Verification chain (updated)

- Descriptor is an ASN.1/DER object; `DCF::Signature` exposes `keyNo()`,
  `signatureBody()`, `signatureLength()`. `asn1D_Signature` in the binary.
- Integrity helpers: `cabot_oad_check_signature` computes **SHA-256** and `memcmp`s it;
  `cabot_oad_verify_textual_digest[_incrementally]` exists for the textual form.
- Signature: RSA. `ICE_CryptoRSAVerify` (0xcafdd8) loads a PEM RSA key, hashes the
  message (SHA1/SHA256) and verifies with `RSA_blinding`/`RSA_verify`.
- Key selection: `ICE_CallistoGetKey(idx, out)` returns slot `idx` (1..9) of 0x100 bytes
  from **.rodata 0x12dd3e6**; consumed via `0x112cea0` / `0x112cf70` (CHIL wrappers).
- Image verification is **not** in userland: `NDFW_VerifyWholeImg` / `NDFW_GetImgSignatureStatus`
  (imported, TEE/secos) plus `TZSysSVC_*` calls.

## 8. Embedded PEM material (checked, benign)

`aurora.elf` contains 27 PEM blocks: 5 RSA private keys, 3 EC private keys, 12 public keys,
5 certificates, 1 DH params. They are **PolarSSL/mbedtls test artefacts**
(`CN=PolarSSL Test CA`, `CN=localhost`, `CN=PolarSSL Client 2`), i.e. library sample data —
their moduli do **not** match any of the 9 OTA key slots. One block is PKCS#8-encrypted.

Conclusion: no vendor signing key is embedded; the OTA key slots stay opaque (public moduli
or TEE-bound material), so custom OTA/firmware remains blocked.

## 9. Can the embedded test keys sign firmware? No

- The 27 PEM blocks are PolarSSL/mbedtls **test** material (`CN=PolarSSL Test CA`,
  `CN=localhost`) living in `aurora.elf` — U-Boot never parses them.
- What U-Boot/TEE actually trust:
  - **TPS vhash**: 32-byte SHA-256 per image, stored in protected storage
    (`nand_tps_read`, `nvt_calc_*_vhash`); kernel compares at boot
    (`nvt_vhash_check` → `VHASH Verify OK`).
  - **`nvt_sign` volume** (253,952 B): starts with **3 × 256-byte signatures**
    (RSA-2048), then padding — one signature per UBI volume (fs0/ap0/ap1).
    Verified by the kernel through TEE (`get_signature_ubi` → SCM), failure is
    `UBI Security Verify volume Fail … goto shutdown`.
  - **secos** (0x6c0000): gzip header is plaintext (even the filename
    `a64m_bsd_rfs.bin`), but the deflate payload is encrypted.
- So a custom fs0/ap0/ap1 needs the vendor private key matching those signatures
  (or a TEE/xboot exploit). None of the keys in the filesystem fit.
