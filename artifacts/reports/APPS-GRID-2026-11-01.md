# APPS-GRID — full-screen portal layout and SVGGrid arithmetic (2026-11-01)

> **Correction 2026-11-05:** navigation code `0x80` constructs
> `FullScreenPortalDialog`, and two shipped paths emit it:
> `doNavigateFullScreenMarket` at `0xd1aa2c` after a market return of `0x29a`,
> and `OperationFinder::handleOperation` case `0x79` at `0xd3e6a0`. The screen
> is reachable, not proven dead. The `+0x1fc/+0x200` runtime-inset

> `HorizontalMaskScaleTransform` before storing named rectangles, and `rowPos`

## Arithmetic

`SVGGrid::calculateHeight(SVGContainer*)` `0x10c9d00`:

```
+0x1f4 = 0; +0x1f8 = 0; +0x1e4 = 0
lookup "mTopL" -> +0x1f4 = y1 - y
lookup "mRowL" -> +0x1e4 = y1 - y
lookup "mBotL" -> +0x1f8 = y1 - y
```

(`EASIRect` fields at +0/+4/+8/+0xc are x/y/x1/y1; the RectangleContainer wrapper
returns those at +8/+0xc/+0x10/+0x14.)

`SVGGrid::renderBackground()` `0x10c9ed0`:

```
if (+0x1e4 > 0) +0x1dc = __aeabi_idiv(h - +0x1f4 - +0x1f8, +0x1e4)   ; rows
if (+0x1e0 > 0) +0x1e8 = __aeabi_idiv(w - +0x1fc - +0x200, +0x1e0)   ; col step
+0x1ec = rowPos.y1 - rowPos.y
```

`__aeabi_idiv` is at `0x1285478` (inside the mislabelled
`FreeStreamMediaPluginInterface_GetModel` symbol): `cmp r1,#0`, `svc`/shift divide,
signed overflow handling. The C `/` on `int` is the same truncation.

`SVGGrid::getButtonPosition(row, col, EASIRect&)` `0x10ca8ac`:

```
x  = col * +0x1e8 + +0x1fc
y  = row * +0x1e4 + +0x1f4
x2 = x + +0x1e8 + +0x200
y2 = y + +0x1ec
```

For the portal (`w=1554`, `h=720`, 5 cols, top/bottom 0, row step 230,
item height 230): rows = 3, column step = 310, buttons (310x230) at col*310,
row*230. With `left=right=0`.

## Button creation and 3-slice rendering (decompiled)

`SVGGrid::drawGrid` (`0x10cabc8`) is exactly:

```
renderBackground(this);   // 0x10c9ed0
createListButtons(this);  // 0x10ca924
createScrollBar(this);    // 0x10ca9c4
update(this);             // 0x10cab70
```

`createListButtons` loops `row < +0x1dc` and `col < +0x1e0`, calls
`getButtonPosition(row, col, rect)`, then the grid virtual `+0x60`
(`makeButton(rect)`) and `SVGGridButtonManager::addButtonItem`. `update` gets
the item count through the grid virtual `+0x54`; `getTotalNumberOfRows` is
`ceil(items / +0x1e0)` (`__aeabi_idiv` plus `__aeabi_idivmod`).

`SVGGridButton::renderBackground` (`0x10ccad0`) resizes its surface to the
button window rect and renders the button SVG as a 3-slice: the left/right
mask pieces are stretched vertically, and the middle piece (`mRowM`) is
stretched horizontally between them. So the grid button window is exactly the
`getButtonPosition` rectangle; the row SVG's named rects are not free-floating
screen coordinates.

Vendor assets for the same widgets are in `artifacts/ui-assets/`:
`gridButton_fa.png` 236x354 (rounded gradient button), `myapps_animated.png`
320x180 (add-app tile; matches `mRowM` 320x180 in FullScreenGridButtonFA),
app art 240x135 or 320x180 (`netflix_animated.png`, `icon_default_app.png`).
These are the `g*` image elements the SVG pack references.

## The resolved state contradiction

`renderBackground`'s per-cell writes feed `getButtonPosition`:

```
x  = col*+0x1e8 + +0x1fc
y  = row*+0x1e4 + +0x1f4
x2 = x + +0x1fc + +0x1e8 + +0x200     ; the second +0x1fc is in the instructions
y2 = y + +0x1ec
```

A naive reading treats `+0x1fc` as `rowPos.x - cell.x` and `+0x200` as
`cell.x1 - rowPos.x1`; for the portal's last cell that gives `-1015/+1005`.
That reading is wrong because it compares raw `rowPos` coordinates with cell
coordinates. `RectHandler::handleSVGElement` applies the active `Transform`
virtual before `RectangleContainer::addRectangle`; for the cell render that is
`HorizontalMaskScaleTransform::transformRect`. The transform subtracts the mask
origin, scales x by `surface_width/mask_width`, and adds the surface origin. Its
mask name is `rowPos` itself, so the stored `rowPos` rectangle is the cell
surface:

```
transformed_rowPos.x  = cell.x
transformed_rowPos.x1 = cell.x1
+0x1fc = horizontal_mask_width_left
+0x200 = horizontal_mask_width_right
```

For `DialogFullScreenPortal`, the top/bottom horizontal masks are
path/polyline elements with no rectangle and the `mRowL`/`mRowR` rectangles are
zero-width, so the resolved insets are zero. The painted grid therefore uses
`col*310 .. col*310+310`, not negative coordinates. The regression in
`openaurora/tests/vendor_grid.c` models the transform for the first and last
cells and preserves a nonzero mask test (5/7). `make check-vgrid` passes.

## Portal grid status: reachable, insets resolved

`commonCreateStep` (`0x10cac10`) sets the column count (`+0x1e0`) before
`drawGrid`, and `drawGrid` calls `renderBackground` **before**
`createListButtons`. `SVGGridButton::create` (`0x10ccdcc`) uses the
`getButtonPosition` rect unchanged. The mask transform above supplies zero
insets for this portal, so the 5x3 `310x230` cell geometry is coherent.

The 2026-11-05 reachability audit shows that navigation code `0x80` does
construct `FullScreenPortalDialog`; the dialog is invokable, not provably dead.
No vendor capture of this grid exists in the artifacts, so stock pixel/layout
parity is still unconfirmed. The operation-0x79 UI mapping and the exact
widget-standard-name map remain open.

Related: `SubLauncherDialog` is a `SettingsDialog` (SVG 189) created by
`LauncherDialog::showSubLauncher` for the focused item's operation/type.
`SettingsDialog` derives from `AnyUIRefreshMessageFullScreenDialog` (widget
175) and its constructor does not set a window offset, so the p0/03 settings
capture is not simply `DialogSubLauncher.listBox` at y=255. The sub-launcher
overlay's on-screen placement still needs its show/position path decoded.

## What is still open

The `HorizontalMaskScaleTransform` path is now decoded for the grid's
`rowPos` mask. The widget-standard-name map
(`SVGWindow::getWidgetStandardName`, `0xeee798`, a conditional 0..0x46 jump
table) is still not fully decoded; the list-box names used by
`SVGListBoxBase::calculateHeight` (widgets 2/5/14/17) are not mapped either.
A corrected stock capture of the portal is still required before claiming stock
pixel/layout parity; the firmware math alone does not establish what the vendor
actually paints on this panel.
