`64c252340d3af6c5d66072611b7bad7a`).

## Arithmetic

`SVGGrid::calculateHeight(SVGContainer*)` `0x10c9d00`:

```
+0x1f4 = 0; +0x1f8 = 0; +0x1e4 = 0
lookup "mTopL" -> +0x1f4 = y1 - y
lookup "mRowL" -> +0x1e4 = y1 - y
lookup "mBotL" -> +0x1f8 = y1 - y
```

(`EASIRect` fields at +0/+4/+8/+0xc are x/y/x1/y1; the RectangleContainer wrapper
returns those at +8/+0xc/+0x10/+0x14.)

`SVGGrid::renderBackground()` `0x10c9ed0`:

```
if (+0x1e4 > 0) +0x1dc = __aeabi_idiv(h - +0x1f4 - +0x1f8, +0x1e4)   ; rows
if (+0x1e0 > 0) +0x1e8 = __aeabi_idiv(w - +0x1fc - +0x200, +0x1e0)   ; col step
+0x1ec = rowPos.y1 - rowPos.y
```

`__aeabi_idiv` is at `0x1285478` (inside the mislabelled
`FreeStreamMediaPluginInterface_GetModel` symbol): `cmp r1,#0`, `svc`/shift divide,
signed overflow handling. The C `/` on `int` is the same truncation.

`SVGGrid::getButtonPosition(row, col, EASIRect&)` `0x10ca8ac`:

```
x  = col * +0x1e8 + +0x1fc
y  = row * +0x1e4 + +0x1f4
x2 = x + +0x1e8 + +0x200
y2 = y + +0x1ec
```

For the portal (`w=1554`, `h=720`, 5 cols, top/bottom 0, row step 230,
item height 230): rows = 3, column step = 310, buttons (310x230) at col*310,
row*230. With `left=right=0`.

## Button creation and 3-slice rendering (decompiled)

`SVGGrid::drawGrid` (`0x10cabc8`) is exactly:

```
renderBackground(this);   // 0x10c9ed0
createListButtons(this);  // 0x10ca924
createScrollBar(this);    // 0x10ca9c4
update(this);             // 0x10cab70
```

`createListButtons` loops `row < +0x1dc` and `col < +0x1e0`, calls
`getButtonPosition(row, col, rect)`, then the grid virtual `+0x60`
(`makeButton(rect)`) and `SVGGridButtonManager::addButtonItem`. `update` gets
the item count through the grid virtual `+0x54`; `getTotalNumberOfRows` is
`ceil(items / +0x1e0)` (`__aeabi_idiv` plus `__aeabi_idivmod`).

`SVGGridButton::renderBackground` (`0x10ccad0`) resizes its surface to the
button window rect and renders the button SVG as a 3-slice: the left/right
mask pieces are stretched vertically, and the middle piece (`mRowM`) is
stretched horizontally between them. So the grid button window is exactly the
`getButtonPosition` rectangle; the row SVG's named rects are not free-floating
screen coordinates.

Vendor assets for the same widgets are in `artifacts/ui-assets/`:
`gridButton_fa.png` 236x354 (rounded gradient button), `myapps_animated.png`
320x180 (add-app tile; matches `mRowM` 320x180 in FullScreenGridButtonFA),
app art 240x135 or 320x180 (`netflix_animated.png`, `icon_default_app.png`).
These are the `g*` image elements the SVG pack references.

## The unresolved state contradiction

`renderBackground`'s per-cell writes make `+0x1fc = rowPos.x - cell.x` and
`+0x200 = cell.x1 - rowPos.x1`, and `getButtonPosition` then computes:

```
x  = col*+0x1e8 + +0x1fc
y  = row*+0x1e4 + +0x1f4
x2 = x + +0x1fc + +0x1e8 + +0x200     ; the second +0x1fc is in the instructions
y2 = y + +0x1ec
```

After the last cell of the portal (col 4, cell.x 1240, cell.x1 1550, rowPos
225..545 in the 1280 template) those are `-1015` and `+1005`, which would put
columns 0..3 at negative x. A fresh grid (zero fields) gives the expected
`col*310 .. col*310+310`. The mix of a 1280-space rowPos with 1554-space cells
also suggests the `RectangleContainer` may return renderer-scaled coordinates;
that is not established. `drawGrid` runs `createListButtons` after
`renderBackground`, so the static call order does not explain how the vendor gets
correct tiles. Resolving this needs either the vendor's grid object state at
runtime (not read while the set is in use) or the on-screen portal; it is not
guessed here.

## Portal grid status: likely dead or broken on this model

`commonCreateStep` (`0x10cac10`) sets the column count (`+0x1e0`) before
`drawGrid`, and `drawGrid` calls `renderBackground` **before**
`createListButtons`. `SVGGridButton::create` (`0x10ccdcc`) uses the
`getButtonPosition` rect unchanged. Therefore the last-cell `+0x1fc = -1015`
would really place columns 0..3 at negative x. Nothing resets those fields
between the two calls.

This is either a genuine bug in the shipped full-screen portal or the dialog is
never used on the D65U546A (it is only reached by a DialogNavigator portal
message; the home screen uses the `SettingItemsListBox` app row instead). No
vendor capture of this grid exists in the artifacts. It should not be
implemented as parity until the vendor screen is actually observed; porting the
broken arithmetic would be wrong for the opposite reason (it would reproduce a
dead screen, not the TV's usable UI).

Related: `SubLauncherDialog` is a `SettingsDialog` (SVG 189) created by
`LauncherDialog::showSubLauncher` for the focused item's operation/type.
`SettingsDialog` derives from `AnyUIRefreshMessageFullScreenDialog` (widget
175) and its constructor does not set a window offset, so the p0/03 settings
capture is not simply `DialogSubLauncher.listBox` at y=255. The sub-launcher
overlay's on-screen placement still needs its show/position path decoded.

## What is still open

The exact mask-width terms (`HorizontalMaskScaleTransform`) and the
widget-standard-name map (`SVGWindow::getWidgetStandardName`, `0xeee798`, a
conditional 0..0x46 jump table) are not decoded; the list-box names used by
`SVGListBoxBase::calculateHeight` (widgets 2/5/14/17) are not mapped either.
Until the `+0x1fc/+0x200` runtime state is confirmed against the vendor (object
read or on-screen portal), the grid must not be rendered from an assumed inset.

## Encoded and tested

`openaurora/common/vendor_grid.c` implements only the verified arithmetic
(visible rows, column step, button rect with caller-supplied left/right).
`openaurora/tests/vendor_grid.c` asserts:

* portal cell grid: 3 rows, 310 step, and with the fresh-grid zero fields
  (0,0,310,230) / (1240,460,1550,690);
* cell rects (renderBackground background paint) and the DialogFullScreenPortal
  chrome/plan: top strip 0,0,1921,162; appsGrid 183,180,1554,720; scrollbar,
  title, logo, paging, portalMode; 5x3 cells of 310x230;
* gridFA margins: rows = (720-16-10)/69 = 10, step = (1280-16)/3 = 421;
* truncation per cell: 94/4 = 23, column 3 = 72;
* zero divisors and NULL are safe.

The test deliberately passes left=right=0 and its output says so; it does not
claim those are the painted portal's runtime values.
