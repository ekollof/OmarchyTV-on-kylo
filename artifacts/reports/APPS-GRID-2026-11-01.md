# APPS-GRID — full-screen portal layout and SVGGrid arithmetic (2026-11-01)

Scope: offline firmware/BinSVG recovery for the vendor full-screen apps portal and
the shared `SVGGrid` placement code. No TV write, no screen implementation.
Addresses are loaded aurora.elf vaddrs (MD5
`64c252340d3af6c5d66072611b7bad7a`).

## Arithmetic

`SVGGrid::calculateHeight(SVGContainer*)` `0x10c9d00`:

```
+0x1f4 = 0; +0x1f8 = 0; +0x1e4 = 0
lookup "mTopL" -> +0x1f4 = y1 - y
lookup "mRowL" -> +0x1e4 = y1 - y
lookup "mBotL" -> +0x1f8 = y1 - y
```

(`EASIRect` fields at +0/+4/+8/+0xc are x/y/x1/y1; the RectangleContainer wrapper
returns those at +8/+0xc/+0x10/+0x14.)

`SVGGrid::renderBackground()` `0x10c9ed0`:

```
if (+0x1e4 > 0) +0x1dc = __aeabi_idiv(h - +0x1f4 - +0x1f8, +0x1e4)   ; rows
if (+0x1e0 > 0) +0x1e8 = __aeabi_idiv(w - +0x1fc - +0x200, +0x1e0)   ; col step
+0x1ec = rowPos.y1 - rowPos.y
```

`__aeabi_idiv` is at `0x1285478` (inside the mislabelled
`FreeStreamMediaPluginInterface_GetModel` symbol): `cmp r1,#0`, `svc`/shift divide,
signed overflow handling. The C `/` on `int` is the same truncation.

`SVGGrid::getButtonPosition(row, col, EASIRect&)` `0x10ca8ac`:

```
x  = col * +0x1e8 + +0x1fc
y  = row * +0x1e4 + +0x1f4
x2 = x + +0x1e8 + +0x200
y2 = y + +0x1ec
```

For the portal (`w=1554`, `h=720`, 5 cols, top/bottom 0, row step 230,
item height 230): rows = 3, column step = 310, buttons (310x230) at col*310,
row*230. With `left=right=0`.

## What is still open

`+0x1fc` and `+0x200` are **runtime fields rewritten inside renderBackground's
per-cell loop**, not description constants. The decompiled code (`DecompAt.java`
on the analysed project) is:

```
for (row...) for (col...) {
    cell = (col*step, row*rowstep + top, cell.x + step, cell.y + rowstep);
    ... render top-left/middle/right masks ...
    +0x1ec = rowPos.y1 - rowPos.y;
    +0x1fc = maskWidth + rowPos.x - (maskWidth + cell.x);   // = rowPos.x - cell.x
    +0x200 = maskWidth2 + cell.x1 - maskWidth2 - rowPos.x1; // = cell.x1 - rowPos.x1
}
```

so after a paint they hold the **last cell's** values. `createListButtons`
(`0x10ca924`) then calls `getButtonPosition(row, col)` for every cell, i.e. the
button rects depend on that last-cell state:

```
x  = col*+0x1e8 + +0x1fc
y  = row*+0x1e4 + +0x1f4
x2 = x + +0x1fc + +0x1e8 + +0x200     ; note the second +0x1fc
y2 = y + +0x1ec
```

For the portal with a last cell at col 4 (cell.x 1240, cell.x1 1550, rowPos
225..545 in the 1280 template) the raw fields are -1015 and 1005, which makes
the first columns negative. A freshly constructed grid has zeroes and yields
col*310 / col*310+310. Which state the vendor actually uses at
createListButtons time is **not established**; it depends on whether the first
renderBackground has run and which cell was last. Do not render the grid from an
assumed inset value. The mask-width terms and the widget-standard-name map
(`SVGWindow::getWidgetStandardName`, `0xeee798`, conditional 0..0x46 jump table)
remain undecoded; the list-box names used by `SVGListBoxBase::calculateHeight`
(widgets 2/5/14/17) are not mapped yet either.

## Encoded and tested

`openaurora/common/vendor_grid.c` implements only the verified arithmetic
(visible rows, column step, button rect with caller-supplied left/right).
`openaurora/tests/vendor_grid.c` asserts:

* portal cell grid: 3 rows, 310 step, and with the fresh-grid zero fields
  (0,0,310,230) / (1240,460,1550,690);
* gridFA margins: rows = (720-16-10)/69 = 10, step = (1280-16)/3 = 421;
* truncation per cell: 94/4 = 23, column 3 = 72;
* zero divisors and NULL are safe.

The test deliberately passes left=right=0 and its output says so; it does not
claim those are the painted portal's runtime values.

Run: `make check-vgrid` (also in `make check`).
