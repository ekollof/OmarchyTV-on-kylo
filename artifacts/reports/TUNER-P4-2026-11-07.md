# Tuner p4 operand fix — 2026-11-07

Scope: close the MEDIUM review finding in `common/nim_tune.c`. Host test and
ARM module build only; no RF source or on-TV tune.

## Defect

`oa_nim_raw_channel_setup_dvbt` copied the raw record's `+0x14` p4 field into
the HAL_Demod_Set block as a boolean:

```c
out->demod[4] = rd32(rec->raw + 0x14) != 0;
```

The recovered record documents p4 as an operand in `0..2` (`nim_tune.h`,
`DEV_NIM_DTV_StartTune`/`FUN_0086aab0`). A request with p4=2 therefore became
1. The builder already rejected p4 outside `0..2` for its own calls, but a
caller-constructed record reached the setup function without validation.

## Fix

```c
uint32_t p4 = rd32(rec->raw + 0x14);
if (... || p4 > 2) return -EINVAL;
out->demod[4] = p4;
```

The value is preserved, and out-of-range records are rejected before any
output is written.

## Tests

`check-tuner-backend` (`tests/nim_tune.c`) now covers:

- p4=0 -> `demod[4]=0`
- p4=1 -> `demod[4]=1`
- p4=2 -> `demod[4]=2` (previously collapsed to 1)
- p4=3 -> `-EINVAL`

Negative check: restoring `!= 0` fails at `setup.demod[4] == 2`. The rest of
the tuner-backend suite (mxl661/NIM/AX/ATV) passes.
