## Specification decisions implemented

Local primary reference: workbench/cec14a.pdf, MD5
db94e71df404736500f529f1a895cac1; its document identifies itself as Version 1.4.
The existing System Audio baseline also uses cec13a.pdf, MD5
f276f28004377aff85c3af1bcae4331a. No CEC 2.0 conformance claim is made.

| Recovered vendor behavior | Specification | openaurora behavior |
|---|---|---|
| Driver command table marks 46/47 broadcast-only (flag 20). | 1.4 Table 18: Give OSD Name / Set OSD Name are directed. Table 29: name is 1..14 printable ASCII bytes (20..7e). | New oa_cec_validate_identity accepts directed messages with correct operands and rejects broadcast/invalid names. |
| Driver table marks 72 direct-only (flag 51). | 1.4 section 13.15 / Table 23 and 1.3a System Audio Control permit broadcast Set System Audio Mode; direct addressing is also used. | Existing audio validator accepts both modes; explicit regression now guards this vendor mismatch. Raw RX avoids VPL's restrictive filter. |
| Driver table/status is not a reliable specification oracle. | 1.4 Tables 13, 21, 29 define physical-address discovery and power-status grammar. | Identity validator checks directed 83/8f requests, broadcast 84 with valid PA/defined device type, and directed 90 with power value 0..3. |

These are **driver-filter defects**, not proof that stock Aurora discards every
valid incoming message: NDAL loses the separate driver result and stock handlers
can still process copied data. Do not turn these findings into an unsupported
claim about end-to-end stock behavior. Existing ARC direction and audio-status
corrections remain in CEC-AUDIO-CONTRACT.

New tests exercise all 256 name-byte values, device-type values and power-status
values, name length boundaries, directed/broadcast modes and explicit unsupported
scope. Six CEC groups plus five audio/prelude groups pass strict host and
ASan/UBSan. Six CEC, four packet and three raw-device injected-I/O groups pass
ARM/qemu; host/sanitizer packet/device checks also pass. CFLAGS retain C11,
-Wall -Wextra -Werror -pedantic. Logs: ../analysis/cec-ownership-2026-11-01/spec-*.

These helpers validate wire grammar. Global source roles, feature availability,
responses, retry timing, System Audio/ARC state machines, workers, device lifetime
and routing remain policy/integration work. No production CEC module is enabled.

The diagnostic finds the firmware-specific controller using both verified vtable

Standard queries to LA8, spaced one second apart:

| TV frame | Meaning | Result |
|---|---|---|
| 08 83 | Give Physical Address | ioctl 0, driver accepted 1 |
| 08 46 | Give OSD Name | ioctl 0, driver accepted 1 |

log counter counts newly seen devices, not every received packet.

## 2026-11-12 Deck suspend/resume observation

The owner tested the stock TV with the Steam Deck on HDMI1:

- Deck sleep: the TV stayed on but left HDMI1 and selected a tuner channel.
- Deck resume: the TV switched back to HDMI1 (correct).

This is consistent with `<Active Source>` (0x82) on resume — the handler calls
`selectSource` — and not with `<Standby>` (0x36), which would only act from the
active device. It is **not** established that `<Inactive Source>` (0x9D) caused
the sleep fallback: an instruction check of `handleCECMessage` @ `0x0102fce0`
shows 0x9D returns unless the TV is already in the standby transition and does
not clear the active source. The sleep tuner switch is the external-interface
disconnect fallback in
[SOURCE-LOSS-FALLBACK-2026-11-12](SOURCE-LOSS-FALLBACK-2026-11-12.md): the
navigator callback reaches `InputManager::handleExternalSourceDisconnected`,
which selects the saved tuner service or the previous external source. The exact
hotplug event and selected tuner service were not captured here. Record it as
stock behavior to reproduce, not as our module's behavior: `mod_cec` currently
handles audio/ARC/user-control only and does not implement 0x82/0x9D routing or
power transitions. Raw instruction excerpt and REA pilot:
`../analysis/cec-first-2026-11-12/rea-2026-11-12.txt`.
