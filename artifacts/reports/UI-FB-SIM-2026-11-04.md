# Offline framebuffer / GPU simulation — feasibility and evidence (2026-11-04)

Question: can the TV framebuffer be simulated with `qemu-arm-static` so the TV
is not needed for every display check?

Answer by layer: **the OSD/fbdev path can be simulated offline (including under
ARM qemu); the GLES composition path can be simulated offline on the host with
Mesa; the vendor Mali output itself cannot be simulated under user-mode qemu.**
No firmware or device state was changed; all runs below are offline.

## 1. fbdev / OSD scanout module — yes, including ARM qemu

`modules/display/display.c` talks to `/dev/fb1` only through `open`, `ioctl`
(FBIOGET_VSCREENINFO/FSCREENINFO, FBIOPAN_DISPLAY and the two vendor region
ioctls) and `mmap`. `tests/display_present.c` already replaces those calls with
`-Wl,--wrap=...` stubs backed by a heap buffer, and drives the **real module**
through its published `display`/`display.alpha` interfaces (BGRA premultiplied
scanout, double/single frame pan, sync/commit failure paths, scene transform).

The same binary builds for the TV ABI and runs under `qemu-arm-static`:

```
make -C openaurora TARGET=tv BUILD=build-tv-v3/fb-sim \
  CC=../artifacts/workbench/gcc-arm-10.2-2020.11-x86_64-arm-none-linux-gnueabihf/bin/arm-none-linux-gnueabihf-gcc \
  build-tv-v3/fb-sim/tests/display_present
qemu-arm-static -L <arm-sysroot> openaurora/build-tv-v3/fb-sim/tests/display_present
```

`artifacts/analysis/fb-sim-2026-11-04/arm-fakefb.txt` records eight groups
passing (exit 0). The fake buffer is sized by the test; a capture harness can
raise it to 1920x1080 and dump the mmap'd BGRA bytes to a file for offline
PNG comparison. This covers composition into the scanout buffer and the pan/
commit protocol — not what the Mali hardware does with the buffer.

## 2. GLES scene composition — yes, on host Mesa (not qemu)

`common/scene_gles.c` uses standard EGL + GLES2, but requests the vendor
display with `eglGetDisplay((EGLNativeDisplayType)1)`. Mesa rejects display 1
(`EGL_NOT_INITIALIZED`), so the plain host probe fails. The repository already
has the adapter `tests/egl_default_display.c`, which maps that production
contract to `EGL_DEFAULT_DISPLAY`; using it (plus `EGL_PLATFORM=surfaceless`,
`LIBGL_ALWAYS_SOFTWARE=1`) runs the **same scene code** on llvmpipe:

```
make -C openaurora scene-gles-mesa
```

`artifacts/analysis/fb-sim-2026-11-04/host-mesa-gles.txt` shows all nine
transition types (identity, x-slide, scale, keystone, clear, fades) with five
uploads/renders/readbacks each, pixel-exact orientation checks, reopen and
cleanup passing (exit 0). This is the rendering path the settings preview uses;
only the vendor rasterization backend differs.

## 3. What still requires the TV

`qemu-arm-static` cannot emulate the Mali GPU or the ntk kernel driver's
`/dev/mali` ioctls, and the toolchain sysroot has no ARM EGL/GLES
implementation other than the shipped `libEGL.so`/`libGLESv2.so`. So:

- vendor-Mali-specific rasterisation, tiling and exact pixel output still need
  the set (or an ARM Mesa cross-build plus its own caveats);
- stock-vs-ours visible acceptance comparisons at the real scanout still need
  a TV capture;
- anything depending on the vendor EGL extensions, MALI_MAU settings or the
  display engine's scanout timing is out of reach for user-mode qemu.

## Recommended split

1. Use `make scene-gles-mesa` and `tests/display_present` for layout,
   composition, transition and pan/commit regressions — no TV.
2. Add a 1920x1080 fake-fb capture harness for offline PNGs of our own
   scanout composition.
3. Reserve TV runs for final visual acceptance and for checks that depend on
   the vendor Mali output; batch them rather than per-slice.

## Limits

The Mesa run is x86 host code, not the ARM ABI; the fake-fb run is the real
ARM module but with a heap buffer instead of the display engine. Neither is
scanout proof, and neither substitutes for stock comparison on the set.
