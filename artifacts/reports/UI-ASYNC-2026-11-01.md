## Firmware and implementation

Existing decompiled/ARM `SVGDialog::onAnimationProgress`10c4dac was rechecked in
`analysis/ui-animation-2026-10-31/oa-animation-effects.txt`:10c4dc0 subtracts1,
10c4dce squares,10c4dd4 computes the cube plus1,10c4de8 caps at1, and10c4dec
calls the framework progress setter. That callback changes the full-screen
transform. Cancel/finalise and dialog teardown remain the separately recovered
contracts from UI-ANIMATIONS/SCENE-DISPLAY. No new hardware API or native renderer
call was introduced. Live Mali hash matches the same firmware extract.

ui_fb holds display.async when present, while retaining both display aliases.
It uses request() for async frames and an owned10ms sampler for latest receipts.
Registration happens in ui_fb lifecycle/deferred rebind, not in another module's
animation callback. The first accepted serial is retained instead of chasing the
latest request; a coalesced later successful UI frame can acknowledge it. Older
receipts and other provider namespaces cannot acknowledge a new UI instance.

ui.ok_file is written atomically with PID/dimensions only after successful CPU
present or successful async frame completion. Queue acceptance, OPEN, errors and
retained old receipts cannot write it. It remains a one-shot process first-frame
receipt, not liveness or independent physical scanout proof. A resumed already
acknowledged instance need not rewrite it. The existing heartbeat is separate.

Async dialog progress now updates/presents the cached canvas; genuine rail/title
changes still repaint, and completion paints the selected screen at identity.
If no scene was painted yet, the first progress paints one. CPU behavior retains
its existing repaint path. New frame submissions never invoke synchronous
present on the async backend. Cancel/navigation behavior is unchanged.

Stop, suspend and provider removal delete the sampler, release/clear async and
display aliases, and reset pending serial state. Failed resume releases both
holds before leaving the UI suspended. Deferred provider return reacquires them
and registers a ui_fb-owned timer. No callback or userdata is given to the GPU
provider; copied receipts and service holds bound lifetime.

## Contract tests

Four strict host, ASan/UBSan and actual-TV injected completion groups:

1. Queue/OPEN/error never acknowledge; an actual successful UI completion writes
   the PID/dimensions file even when newer paints are queued.
2. Old receipts cannot acknowledge a reloaded UI. Suspend/failed resume release
   both service holds and sampler; retry succeeds.
3. Forced display removal drops aliases/callbacks; provider return rebinds without
   stale pointer use. Normal provider unload is blocked by UI holds.
4. Controlled dialog midpoint uses cubic0.875 and the same image revision/upload;
   completion submits a changed selected-screen image at identity. This tests
   cache/repaint behavior, not a screen emulator.
