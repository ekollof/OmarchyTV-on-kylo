# Stock UI assets and layout — extracted from the firmware — 2026-10-30

Parity target: the native UI should first look and behave like the vendor's, then diverge. That means
using the vendor's own artwork and geometry rather than redrawing from screenshots. Both are in
`/vendor2/dynamic_ui` (volume `ap1`, extracted with
`artifacts/scripts/extract_from_dump.sh vendor2:/dynamic_ui`).

## What is in the theme pack

| file | size | what it is |
|---|---:|---|
| `default.ui` | 254 B | the manifest: lists the packs below, then `V.0.51.52.3` and the theme name `telefunken18` |
| `telefunken18_img.txt` / `.bin` | 47 KB / 5.6 MB | **974 image entries**; the txt is the index, the bin is the concatenated data |
| `telefunken18_svg.txt` / `.bin` | 10 KB / 290 KB | **702 layout records** — not SVG, see below |
| `telefunken18_font_byte_data.txt` / `.bin` | 280 B / 30 MB | the font glyph data |
| `telefunken18.img` | 613 B | small pack describing the image set |

## Image pack — fully extracted

Index line format:

```
<type> <name> <hash> <w> <h> <size> <flag>
1 icon_tv.png 0x337d9bb7 36 36 321 0
```

The `.bin` is simply the assets **concatenated in index order**, so the offset is cumulative and the
6th field is the entry size (verified: 198 then 519−198 = 321, 769−519 = 250, …).

Result: **964 PNGs, 6.8 MB**, written to `artifacts/ui-assets/` — the complete stock UI artwork
(`4k_HDR_IMMERSIVE_enabled.png`, `ai_animated.png`, `airmouse_hitachi_enabled.png`, source and app
icons, badges, arrows …). Ten index entries are not PNG (empty slots) and were skipped.

## Layout pack — the interesting one

`telefunken18_svg.bin` is **not vector art**. It is the stock UI's layout description, in a compact
record format: a length-prefixed name followed by properties. Decoded samples:

```
background    #FFFFFF   … matrix-like coords
title_gRowL   #BE1E2D
title_mRowL   #000000
rowItems      mRowM … #000000 none … text … #000000 none
text          … #000000 none
image         /png/picture.png  matrix(0.9999 0 0 0.9999 13 4)
```

so it carries **element names, colours, geometry and image references** for the stock screens. That is
exactly what "replicate the layout numbers instead of eyeballing screenshots" needs.

Copies of the manifest, the layout pack and both indexes are in `artifacts/ui-assets/_layout/`
(the 30 MB font pack was left on the extracted image).

## Translations

`/vendor2/mb230_langprofile.bin` (5.17 MB) is another **EFSL** container (`magic "EFSL"`, entry name
`langprofile`), but unlike the theme it is **not compressed**: it holds the UI translations as
NUL-separated UTF-8. Each string id is stored as a **run of translations, one per language**, in a fixed
language order — e.g. for "Settings":

```
Settings · Vendosjet · Parametrlər · Наладкі · Podešavanja · Настройки · Podešavanja
        · Nastavení · Indstillinger · Instellingen · Seaded · Asetukset · (empty) · Réglages …
```

Dutch `Instellingen` sits at slot 12 of that run, with an empty slot ahead of French, so exact per-language
alignment needs the language enum rather than raw counting.

Extracted for reference: `artifacts/ui-assets/_layout/lang-strings.txt` — **70,948 fields, 59,359 unique**
(56,715 look like real UI text). That is every label, dialog and error message the set can show, in every
language it supports, available offline.

(For a first parity UI, English strings can be paired by id; Dutch needs the enum, or a lookup of a known
pair per run.)

## Using it

* `mod_ui_*` can draw with the real PNGs through the `display` service (`fill`/`present`), once a PNG
  decoder is added — the smallest option is to pre-convert the icons we need to raw pixels at build
  time rather than shipping a decoder.
* The layout records are the reference for the stock portal's grid: element names line up with the
  `LauncherItem` rows in `settingsDB.db`, so tile geometry can be taken from here rather than measured.
* Nothing here is redistributed: `artifacts/ui-assets/` is device data from our own set.
