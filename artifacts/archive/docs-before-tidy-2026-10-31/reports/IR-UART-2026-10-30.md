# How the remote reaches the TV (and how a native shell gets it) — 2026-10-30

This was the open risk for a native launcher in front of aurora: `/dev/input` only has `mice`, so
there is no evdev path to the remote. Reversed offline from
`ap0/lib/dfb/directfb-1.7-1/inputdrivers/libdirectfb_nvt_uart_ir.so` (14 KB, **symbols intact**) and
the `DEV_UART_*` / `_micom_*` symbols in `aurora.elf`.

Good news: the input path is a plain serial port with a simple fixed frame. A replacement UI needs
neither DirectFB nor DIAL to read the remote.

## The stack

```
IR receiver / front panel
   -> MCU
      -> /dev/ttyS2    115200 8N1, raw — 9-byte frames
         -> aurora:  _micom_receive / DEV_Uart_GetKey*,  DEV_UART_IR_*
            -> DEV_UART_SendDFBKey  ->  /tmp/myfifo   (20-byte records)
               -> libdirectfb_nvt_uart_ir.so  (Dev_Uart_GetKey4, 20-byte reads)
                  -> dfb_input_dispatch -> DirectFB -> aurora UI
                     (ICE_RemoteRegisterKeypressFunction / ...KeyreleaseFunction)
```

`aurora.elf` is the only binary that owns `/dev/ttyS2` (it also references `/dev/ttyS0`); the DFB
input module never touches the UART. It reads **files/FIFOs** and dispatches what it finds.

## The serial port

`nt72668_micom_receive_cmd3()` — `open("/dev/ttyS2", O_RDWR|O_NOCTTY)`, then a hand-built termios:

| field | value |
|---|---|
| `c_iflag` | `0x0` (no software flow control, no CR/NL translation, no strip) |
| `c_oflag` | `0x0` |
| `c_cflag` | `0x18b2` = **CS8 · 1 stop · no parity · CREAD · CLOCAL · B115200** |
| `c_lflag` | `0x0` (raw, no echo, no ICANON, no ISIG) |
| `c_cc[VMIN]` | `1` |
| `c_cc[VTIME]` | `0` |

then `tcflush(fd, TCIFLUSH)` and `tcsetattr(fd, TCSANOW, …)`. Reads are plain blocking `read(fd,&c,1)`;
the port is re-opened per call, so it is not held open.

## The frame (9 bytes)

```
FF FF TT A1 A2 CC ~CC B7 B8
 │  │  │  └──┴── NEC extended: address 0x66 0x11, command, ~command
 │  │  └──── event type: 0x50 = key, 0x5E = other (carries the raw byte in A1)
 │  └─────── sync (two 0xFF bytes; the reader skips a run of 0xFF)
 └────────── sync
```

`B7`/`B8` are still unaccounted for (length 9 is fixed; they are probably repeat/long-press state).
`0x5E` frames are handled differently: the vendor code stores the raw `A1` byte as the key value and
clears the "repeat" flag, so it is most likely a release/long-press marker rather than a button.

There are two decoders in the module, which matters if the frame is ever unexpected:

* `Dev_Uart_GetKey()` — matches **`A1` alone** against `ss_keycode_map` (52 small values);
* `Dev_Uart_GetKey3()` — matches the **whole 4-byte NEC code** (`A1 A2 CC ~CC`) against
  `nec_keycode_map` (52 entries).

## The remote

NEC extended, address `0x66 0x11`. `nec_keycode_map` (`.rodata 0x1800`, 52 × u32) holds the packed
frames; **all 52 satisfy `cmd ^ ~cmd == 0xFF`**, which confirms the structure. The parallel
`custom_keycode_map` (`.rodata 0x18d0`, 52 × u32) holds the key symbol the driver reports: ASCII
`0x30`–`0x39` for digits, `0x0d` for OK, `0xf000`–`0xf105` for everything else.

## Three ways to inject a key (no remote needed)

These are the vendor's own test paths, all readable from the module:

| path | format | read by |
|---|---|---|
| `/mtd_apdat/irsim` (= `/conf/irsim`) | streaming `FF A B (A^B)` — sync on `0xFF`, 16-bit code `(A<<8)\|B`, XOR checksum | `nvt_pipeEventThread` |
| `/tmp/kp_fifo` | 12-byte records: `[0]=status [1]=? [4..7]=code [8..11]=type` (4=press, 1=release, 8=repeat) | `Dev_KP_GetKey` / `nvt_KeyPadEventThread` |
| `/tmp/myfifo` | 20-byte records, what aurora writes for the DFB driver | `Dev_Uart_GetKey4` / `nvt_remoteEventThread` |

`/mtd_apdat/irsim` is the interesting one: aurora exposes `DEV_UART_IR_Sim_*`
(`Sim_IsRunning`, `Sim_STR_ONOFF`, `Sim_SetRcType`, `Sim_Task_Start`) and the thread only starts if the
file exists. Being able to *inject* keys is also useful for driving the stock UI from a script without
DIAL, and for testing the launcher against the real input path.

## What this means for the native shell

* Input is **solved in principle**: while our shell owns the screen, `aurora` is not running, so
  `/dev/ttyS2` is ours alone. Read the 9-byte frames and map `cmd` → action. No DirectFB, no DIAL, no
  browser, no latency.
* Ownership is naturally exclusive, which fits the exec model exactly: our shell holds the port, and
  on handover it **must close the fd** (or set `O_CLOEXEC`) before `exec`ing aurora, otherwise both
  processes compete for bytes.
* We get long-press and repeat for free once `B7`/`B8` are understood, and the power key is in the
  same table (`DEV_UART_IR_EnableLongPressPowerKey` / `GetLongPressPowerKeyStatus` exist in aurora).

## Tool

`launcher/osdprobe/irkey` (static ARM, built):

```sh
irkey                  # decode frames, print each key, summary table on Ctrl-C
irkey --raw            # hexdump only
irkey --timeout 60     # stop after 60 s
```

While it runs it consumes bytes the stock UI would have seen, so run it when the set is idle (or
before `aurora` starts). It changes no state.
