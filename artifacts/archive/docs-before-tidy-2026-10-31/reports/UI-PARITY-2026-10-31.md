# UI parity + the OSD ownership problem (2026-10-31)

Result of the round that started with "the colors are wrong though, and it looks nothing like the
vendor aurora ui/ux". Two separate findings: a real bug in our own capture tool (fixed, and the UI
now matches the stock portal to within 1.6/255 mean pixel error), and an architectural gate that
stops us showing it on the panel while the vendor UI is running.

## 1. The colour bug was in `tools/tvshot.py`, not in the renderer

`tvshot.py` decoded every 32bpp layer as **RGBA**. The layer is **BGRA** (`byte0 = blue`), which was
already measured with `tools/colorbars` (three bands of `byte0=255`, `byte1=255`, `byte2=255`) on the
panel: left came back **blue**, middle **green**, right **red**.

Consequence: every reference capture we own had red and blue swapped, so
`artifacts/protocol/shot-launcher.png` showed a blue→purple rail with a blue Netflix logo, and that is
what the palette in `ui_fb` was sampled from. The stock portal really is:

| rail item | sampled from the swapped capture | actual colour |
|---|---|---|
| 1 | `(30,148,247)` | `#f7941e` `(247,148,30)` |
| 2 | `(41,90,241)` | `#f15a29` `(241,90,41)` |
| 3 | `(45,30,190)` | `#be1e2d` `(190,30,45)` |
| 4 | `(36,25,129)` | `#811924` `(129,25,36)` |
| 5 | `(48,23,72)` | `#481730` `(72,23,48)` |

Independent confirmation: `#BE1E2D` is a literal value in the vendor style pack
(`/vendor2/dynamic_ui/telefunken18_svg.bin`, properties `title_gRowL`, `title_mRowL`, `itemPos`, …).
The corrected palette reproduces a value the firmware itself carries, which the swapped one did not.

Fixed:
* `tools/tvshot.py` — default order is now `BGRA` for 32bpp layers, with the colourbar evidence in
  the comment. `--format RGBA` still available.
* `artifacts/protocol/shot-launcher.png` — red/blue corrected in place; the pre-fix file is kept as
  `shot-launcher.as-captured.png` for provenance.
* `openaurora/modules/ui_fb/ui_fb.c` — corrected palette.

## 2. The layout is the portal's, not an invention

Measured off the corrected capture:

| element | geometry |
|---|---|
| background | `rgb(14,14,13)` |
| title | "Startpagina", ink at `x 29..290, y 80..133` (262×54) |
| rail | 5 slots, `x 24..144`, first at `y 211`, **120 px each** |
| rail, focused | grows to **150×150** at `x 11..160`, pushes the slots below down, and gets a 5 px accent frame `#f7941e` |
| rail glyphs | white line art, centred, 55–78 px |
| cards | 9 cards, `171×95`, `x 209 + i*190`, `y 478` (16:9, so logos scale exactly) |

The rail glyphs, the app logos and the title are all the set's own content:

* glyphs cut from the device's portal framebuffer (white on coloured tile → alpha recovered by
  projecting the pixel onto `white - tile`, so the antialiasing survives);
* cards from `/buffer/downloaded_images/launcher_app_thumb<N>`, the PNGs the stock portal downloaded
  for its own `LauncherItem` rows — the same nine, in the same order, as the DB rows with
  `m_item_type=2 AND m_parent_id=1` (Netflix, Prime Video, YouTube, tabii, Canal Digitaal,
  TV Vlaanderen, TÉLÉSAT, Digiturk Play, GAIN);
* title rendered with `/vendor/fonts/DefaultProportional.ttf` (DirectFB's own default face, best
  match of the 33 fonts in that directory).

`openaurora/tools/mk-ui.py` builds all of it into the flat `OAI1` blobs `ui_fb` blits, so nothing on
the TV needs a PNG decoder.

### Measured parity

`ui_fb` painted on the set, layer read back with the fixed `tvshot`, compared to the corrected
reference:

```
whole frame   mean |Δ| 1.62/255   (0.6 %)
  background        0.67
  cards             3.22     (logo edges, 1 px)
  rail              5.71     (glyph antialiasing)
  title            12.46     (font: not the exact vendor face)
```

Per-card mean colour agrees within 1–2 counts, e.g. card 5 `(250,74,38)` vs `(250,75,39)`.

## 3. Why it cannot be *held* on the panel: both OSD layers belong to aurora

What was tried, and what each proved:

| attempt | outcome |
|---|---|
| paint fb1 once | visible, then the vendor UI repaints over it |
| mirror fb1 into both frames | stable until aurora repaints |
| add `FBIOPAN_DISPLAY` | **flicker**: our own flip made DFB flip back — hence `display.pan=0` |
| paint fb0 (`.directfbrc` says layer 0 is `middle,upper`) | the "Geen signaal" box still drew on top → **fb1 is the upper layer** |
| repaint at 4 fps / 20 fps | horizontal strips: aurora repaints **partial regions**, we write whole frames |
| `SIGSTOP` vendor aurora | **set reboots** — MCU watchdog, no kicker left |

The vendor's no-signal banner carries a live clock, so it repaints fb1 about once a second, and it
does so with dirty-rectangle updates. A second writer of whole frames can therefore never win: the
two update models interleave.

So on-panel verification of a standalone UI is blocked on **replacing aurora as the OSD owner**, not
on drawing code.

## 4. The watchdog is the gate — and it is almost reachable

`libNDAL_EX.so` exports the MCU watchdog surface:

```
NDAL_VideoExt_STBC_SetWDT                 NDAL_VideoExt_STBC_StopWDT
NDAL_VideoExt_STBC_FreshWDT               NDAL_VideoExt_STBC_GetMcuWatchDogTimeout
NDAL_VideoExt_STBC_ResetByHWWDT           NDAL_VideoExt_STBC_SetMcuWatchDogTimeout
```

`StopWDT`/`FreshWDT` take no arguments (disassembled: `r0` is spilled and never read), i.e. they look
callable from outside aurora. Anti-result: a probe (`/tmp/opencode/probes/wdtprobe.c`) that
`dlopen`ed the library with `RTLD_LAZY` and called `GetMcuWatchDogTimeout` was killed and the set
**rebooted**, twice. The STBC path goes through `ndcommon_v4l2_config_ctrl` and clearly expects the
v4l2/STBC device to be opened and configured first — aurora does that as part of its PLAT init, we
called it cold.

That is the concrete next step, and it is a firmware-reading job, not a guessing job:
1. read how aurora initialises the STBC/v4l2 node before `PLAT_SYS_KickWatchDog`
   (`PLAT_SYS_SetMcuWatchDogTimeout`, `PLAT_SYS_StopMcuWatchDog` are in the binary, stripped);
2. reproduce that order in a `wdt` module and only then try `SIGSTOP` again;
3. hook test mode (`/conf/ui_test` marker in `run_aurora.sh`) that starts openaurora instead of the
   vendor UI, with an auto-revert counter like `/conf/launcher_fail` so a bad boot heals itself.

Until then, the honest verification path is the framebuffer compare above — which is why the parity
numbers exist.
